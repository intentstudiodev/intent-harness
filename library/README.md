# Library

Short, sourced notes on the kinds of products people build and the areas every product touches. **A lens, not a rulebook:** a library file helps you ask better questions, notice what is usually there and know where to read deeper. It never overrides the owner or the evidence, never becomes a card by itself, and never stops you from thinking past it. Products differ; the file describes what is common, not what is right.

## Two shelves

| Shelf | What a file describes | Groups |
|---|---|---|
| `domains/` | what the product is. A product has **several domains**: an internal marketplace with booking and a community is Marketplace + Booking + Social, audience Internal | `model` (how it works: marketplace, booking …) · `sector` (the world it lives in: health, finance …) |
| `areas/` | **Area knowledge**: what a product is made of and where it runs | `platforms/` · `architecture/` (Product Architecture at C4 context and container level) · `design-systems/` · `patterns/` · `parts/` · `practices/` |

`index.md` lists every file in one line (generated by `node core/index.mjs`). Read the index, then only the files that match the project: its domains, audience, platforms, design library and the parts in scope. A handful at a time, never the whole shelf.

## One shape for every file

Every file is built from the same parts in the same order (`template.md`). A file leaves out a section that would be empty; it never adds new ones.

| Part | What goes there |
|---|---|
| frontmatter | `kind: library`, `shelf`, `group` (domains only), `name`, `fits when`, `related`, `checked` (year-month) |
| opening paragraph | what it is, in two or three sentences, and the tension at its heart |
| **Questions worth asking** | questions, each with why it matters; the owner's answers decide, not the file |
| **Usual shape** | what is often or sometimes there: roles, journeys, screens, rules for a domain; anatomy and conventions for an area. Each line marked `often` or `sometimes`: how common, not how right |
| **Choices and trade-offs** | real alternatives and when each fits |
| **Watch out** | mistakes that recur, and why they hurt |
| **Go deeper** | named sources and what each is good for: the directions to learn more |
| **Related** | other library files, by path |

**Voice.** Plain words, short lines, observations not orders: "often", "teams usually", "consider", "it depends on". No "must", "always" or "never" unless it is a fact, such as a law or a platform's store rule, and then the source is named. One to two pages per file.

**Sources.** Official guides first (platform guidelines, standards, laws), then established research (usability studies, published practice), then vendor documentation, then teardowns of real products. Written in our own words with links; never copied. `checked` says when the sources were last read.

## Learning while you work

- **Yours.** Something learned in a project that would help in the next one ("in clinics, the front desk books for patients") → offer: "Shall I remember this for future projects?" On yes: one line, dated, in `tweaks/library/<the same path>.md`. It is read beside the shipped file and wins where they disagree. Upgrades never touch it.
- **Everyone's.** A shipped file that was wrong, thin or out of date → an improvement note tagged `library: <path>` (`self-improvement/retro.md`). `share-note` anonymises it and, on your yes, opens an issue under your own login. Nothing is sent on its own.
- **Fresh.** A file whose `checked` is more than a year old, used with web access: read its Go deeper sources again before leaning on it, and note what changed as a library note.

Contributions: a pull request with a file in this shape, or the issue form *Library file*.
