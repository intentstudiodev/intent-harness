# use-library

1. **Pick.** Read `library/index.md`. Choose the files that match what is known: the project card's domains (`industry:`) and `audience:`, the platforms, the design library, the parts in scope. Read those, plus `tweaks/library/<same path>.md` when it exists (the user's own notes win). A handful, never the shelf. Nothing matches → say so; do not invent a file.
2. **Use as a lens.** Questions worth asking feed the interview and the gap round, in the owner's words, only where the owner has not answered already. Watch out lines inform your own suggestions and critique. Go deeper names where to read more when a topic needs depth: offer it, do not assume it.
3. **Offer the usual parts once** (setup's *Typical parts*, `knowledge/start-project.md`): items marked `often` and `sometimes` from the matching files, as checkboxes, the file's why in the description. Ticked → the owner confirmed it (unmarked; the owner is the source, the file was the suggestion). Unticked → a line in the research notes so it is not offered again.
4. **Stay free.** A library line is never a fact about this product, never a card by itself, never a reason to overrule the owner, the documents or the code. When the product does something unusual, that is information, not a mistake. A running product (`research/map-existing.md`) gets no library suggestions: what looks missing goes to `sandbox/ideas.md`.
5. **Learn.** What this project taught that a library file lacks → the two offers in `library/README.md` (*Learning while you work*): yours in `tweaks/library/`, everyone's as an improvement note tagged `library: <path>`.
