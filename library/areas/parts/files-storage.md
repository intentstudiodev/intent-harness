# Files and storage

What happens to a file after someone picks it: the upload, the checks, where it lives, who can fetch it, how long it stays and what happens when it is deleted. The picker, previews and galleries are in the media upload pattern. The tension: files are user content of unknown size and unknown intent, served back to other people, and storage that is cheap per gigabyte becomes expensive per mistake.

## Questions worth asking

- What kinds of files, and how large, typically and at most? A profile photo, a 4 GB video and a folder of PDFs are three systems.
- Who may see a file: only the uploader, a team, anyone with a link, the public? Is that decided per file or by where it sits? It decides the permission model.
- Are files edited in the product, versioned, or only stored and downloaded? Editing and versions turn storage into a document system.
- Must files survive offline, on mobile, or across devices with sync? Offline and sync add conflict handling and storage limits.
- How long are files kept, and what happens on account deletion or plan downgrade? Are there legal retention rules? Retention ties storage to billing and the law.
- Do files carry personal or sensitive data (IDs, health records, photos with location)? It changes scanning, encryption and region.

## Usual shape

### Anatomy
- upload straight from the client to object storage with a short-lived signed URL · often · keeps large files off the app server
- resumable or chunked upload for large files · sometimes · flaky mobile networks; the tus protocol is one open option
- server-side checks after upload: type, size, malware scan · often
- stored name generated by the system, original name kept as metadata · often · OWASP: avoids path and overwrite tricks
- derived files: thumbnails, previews, compressed versions · often · made in the background
- metadata record per file: owner, size, type, checksum, where it lives, who can read it · often
- access through the product (a check, then a short-lived download link) · often
- quotas per user or plan with a usage meter · sometimes
- versions and trash with restore · sometimes · documents and shared folders
- retention and deletion jobs, including derived files · often · the part most often left until later

### Conventions
- an allowlist of file types, not a blocklist · often · OWASP File Upload Cheat Sheet
- the browser's content type and the file extension treated as hints, not facts · often
- images decoded and re-encoded, which also strips location metadata · sometimes · protects privacy and removes some attacks
- user files served from a separate domain or with download headers · often · uploaded HTML cannot run as your site
- signed URLs that expire · often · on S3 at most seven days with long-term keys, often minutes in practice; a signed URL is a bearer token
- erasure requests that reach file copies, previews and backups · often · EU and UK GDPR; backups can be put "beyond use" until overwritten

## Choices and trade-offs

- **Through your server or straight to storage.** Proxying lets the server check every byte and costs bandwidth and memory; direct upload scales and needs checks after the fact, with the file quarantined until they pass.
- **Public URLs or signed access.** Public URLs are cacheable and simple; signed links protect private files and expire, which breaks links pasted into email or chat. Many products mix: public for avatars, signed for documents.
- **Object storage, a file service, or the user's own cloud.** Object storage is cheap and plain; a managed file service adds transforms and a dashboard; storing in the user's Drive or iCloud keeps data with them and gives you less control.
- **Keep everything or expire.** Keeping forever is easy and grows cost and risk; retention rules need explaining and an export before deletion.

## Watch out

- Trusting the extension or the content type · a script named photo.jpg
- Serving uploads from the main domain · uploaded HTML or SVG can run as your site
- Deleting the record but not the file, or the original but not its thumbnails · storage grows and "deleted" data lingers
- Guessable file URLs or IDs · anyone can walk through other people's files
- No size limit, or limits checked only in the browser · one upload fills the disk; archives can expand far beyond their size
- Location and camera data left in shared photos · reveals where people live
